# 上游访问受阻：Cloudflare Workers 被 WAF 拦截

## 现象

从部署在 Cloudflare Workers 上的店面访问上游站点，**任何路径**都返回：

```
HTTP 456
server: cloudflare
<script src="/_guard/html.js?js=p456"></script>
```

同一时刻从住宅/代理 IP 访问同样的 URL，全部返回 200。

## 判定

`_guard/html.js` 是 JS 挑战型 WAF：要求客户端执行 JavaScript 才放行，
用于拦截自动化流量。三组不同的请求特征（裸请求、完整浏览器头、XHR 头）
结果完全一致，**说明拦截依据是来源 IP 段，不是请求特征**。

关键的一点是：**公开目录接口与 `/shared/*` 对接接口一视同仁地被拦**。
所以这不是「拿到 app_id/app_key 就能解决」的问题 —— 凭据解决的是鉴权，
而这里连 TCP 之上的 HTTP 响应都拿不到。

复现方式（需要 ADMIN_TOKEN）：

```bash
curl -H "Authorization: Bearer $ADMIN_TOKEN" \
  "https://<你的站点>/api/admin/probe?url=<上游URL>"
```

探针只允许探测配置里已有的上游域名，不会变成开放代理。

## 不做的事

不实现 JS 挑战破解、IP 轮换或代理池来绕过这道闸。上游是**主动部署**了
这个拦截的，绕开它等于规避对方明确设置的访问控制。即便技术上可行，
这类方案也极其脆弱：对方调一次策略就全线失效，而失效的表现是
「店面静悄悄地卖不了货」。

## 可行的路径

### 1. 联系上游站长（推荐）

对接功能本来就是给合作方的机器调用设计的，站长大概率遇到过这个问题。
需要同时谈两件事：

- 申请 `app_id` / `app_key`
- **说明你的请求来自 Cloudflare Workers，请求放行**

如果对方无法按 IP 放行（Cloudflare 的出口是巨大的共享池，确实难以白名单），
就走下面第 2 条。

### 2. 中继层

在一台上游不拦截的机器上跑一个极薄的中继：

```
店面 (Workers)  ──签名请求──▶  中继 (你的服务器)  ──▶  上游
```

中继只做两件事：持有上游凭据、代为转发。它不碰订单、不碰钱，
挂了也只是暂时同步不到目录与发不了货，不影响已有数据。

这与「绕过 WAF」的区别在于：这是**授权合作方从自己的服务器发起调用**，
是对接功能的正常用法，而不是伪装成浏览器去骗过挑战。

实现上对店面是透明的 —— 新增一个 `driver: relay` 的适配器即可，
业务代码一行不用改。

### 3. 换一家上游

`SupplierAdapter` 接口就是为此准备的。换成不拦截 Cloudflare 的上游，
只需改配置里的 `domain` 与凭据。
